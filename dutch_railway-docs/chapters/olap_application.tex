\section{OLAP Application}
\label{sec:olap_application}

To make an OLAP application that provides use to society, we focused our application on the reliability of the different entities involved in the Dutch railway system. After a look at the database, the best metric provided to measure reliability is the delay of the train to its stop on arrival and on departure.

The queries below are shown in their base form. Filters selected in the application (companies, date range, time of day, number of results) are added as extra conditions at run time, and the places where this happens are marked with comments.




\subsection{Report 1: On-Time Trends}
\label{subsubsec:on-time_trends}
The first report shows the on-time rate of all selected companies per quarter, month, and week.

In the application, there is a bar graph showcasing the difference in on-time rate. Upon initial load, the bar graph shows the data in relation to each quarter of the year. Once the user clicks on it, it shows the data in relation to each month of the selected quarter, and then the user can select a month to view the data in relation to the weeks of that month.

The operation from going to a larger to finer grain (such as quarter to month) is a \emph{drill-down}, whereas going from a finer to larger grain (such as week to month) is a \emph{rollup}. In this query, the smallest grain is the data per-week. After the per-week data, it gets aggregated to per-month, then per-quarter. In the query, the ROLLUP construct was used, formatting the resulting table in a manner that shows information in the three different grains.

The user can also choose the companies to include and the reporting period. Restricting the company dimension to a chosen set of companies and the date dimension to a chosen range is a \emph{dice} operation.

The corresponding SQL query used in this report is as follows:

\begin{lstlisting}
WITH cur AS MATERIALIZED(
    SELECT
        fsv.company_name,
        wm.min_quarter AS quarter,
        wm.min_month AS month,
        d.week,
        COUNT(*) AS total_stops,
        ROUND(100.0 * SUM(CASE WHEN fst.arrival_delay = 0 THEN 1 ELSE 0 END) / COUNT(*), 2) AS on_time_rate

    FROM fact_stop AS fst
    JOIN fact_service AS fsv ON fsv.rdt_id = fst.rdt_id
    JOIN dim_date AS d ON d.date_key = fsv.date_key
    JOIN (
        SELECT week, MIN(quarter) AS min_quarter, MIN(month) AS min_month
        FROM dim_date
        GROUP BY week
    ) AS wm ON wm.week = d.week

    WHERE fst.cancel_status IN ('none', 'departure-only')
    AND fst.arrival_delay IS NOT NULL
    GROUP BY fsv.company_name,
    ROLLUP (wm.min_quarter, wm.min_month, d.week)
)

SELECT
    cur.company_name,
    cur.quarter,
    cur.month,
    cur.week,
    cur.total_stops,
    cur.on_time_rate,
    ROUND(cur.on_time_rate - prev.on_time_rate, 2) AS rate_change
    
FROM cur
LEFT JOIN cur AS prev
ON prev.company_name = cur.company_name
AND (
        (cur.month IS NULL AND cur.quarter IS NOT NULL
        AND prev.month IS NULL AND prev.quarter = cur.quarter - 1)
    OR
        (cur.week IS NULL AND cur.month IS NOT NULL
        AND prev.week IS NULL AND prev.month = cur.month - 1)
    OR
        (cur.week IS NOT NULL AND prev.week = cur.week - 1)
    )
ORDER BY cur.company_name, cur.quarter, cur.month, cur.week;
\end{lstlisting}

This report lets users see whether reliability is improving or worsening over time.




\subsection{Report 2: Company Monthly Rank by On-Time Rate}
\label{subsubsec:company_monthly_rank_otr}
The second report details the on-time rate of each selected company, including each company's rank based on their on-time rate, per month, on a chosen time of day.

In the application, the user is able to pick which time-of-day to filter the data on. There is a line graph generated in the application. A line represents a company, and hovering over it highlights that company. The user is additionally able to filter which companies to include in the report.

As the performance of the railway system differs at the different times of day, restricting it to show only stops from the morning, afternoon, or night allows a more specific analysis of how companies operate at different times. The explicit rankings make it easier as well to identify which companies perform best at different times, and whether the best-performing company changes depending on the time.

The OLAP operation used is \emph{dice}. The time-of-day dimension is fixed on a single value dependent on user input, and removes all data corresponding to times that are not within the selected time by the user, additionally, the company dimension is cut and data of companies filtered out by the user are not included. The removal on multiple dimensions constitute this report as a dice operation, rather than a slice.

The corresponding SQL query used in this report is as follows. Note that this is the base SQL, including only the filter on time of day. The filter for company filtering is done separately in the application itself:

\begin{lstlisting}
WITH cur AS MATERIALIZED(
    SELECT
        fsv.company_name,
        d.month,
        ROUND(100.0 * SUM(CASE WHEN fst.arrival_delay = 0 THEN 1 ELSE 0 END) / COUNT(*), 2) AS on_time_rate,
        ROUND(AVG(fst.arrival_delay), 2) AS avg_arrival_delay

    FROM fact_stop AS fst
    JOIN fact_service AS fsv ON fsv.rdt_id = fst.rdt_id
    JOIN dim_date AS d ON d.date_key = fsv.date_key
    JOIN dim_time AS t ON t.time_key = fst.arrival_time

    WHERE fst.cancel_status IN ('none', 'departure-only')
    AND fst.arrival_delay IS NOT NULL
    AND t.time_of_day = 'morning' -- THIS WHERE CLAUSE CAN CHANGE DEPENDING ON SELECTED TIME

    GROUP BY fsv.company_name, d.month
)

SELECT
    cur.company_name,
    cur.month,
    cur.on_time_rate,
    cur.avg_arrival_delay,
    1 + (
        SELECT COUNT(*)

        FROM cur AS better
        WHERE better.month = cur.month AND better.on_time_rate > cur.on_time_rate
            
    ) AS rank

FROM cur

ORDER BY cur.month, rank;
\end{lstlisting}

This report shows which companies are most reliable at different times of the day.





\subsection{Report 3: Underperforming Trains in Companies}
\label{subsubsec:underperforming_trains}
The third report focuses on the performance of trains under a specific company. The average arrival delay of a company throughout all of its stops is recorded. The average arrival delay per-train, and the difference of the company average and train average is calculated to see which trains perform worst in each company, relative to the company average.

In the application, the user can pick a company and a number $n$, alongside a date range to select where they want the data to be gathered from. The average company arrival delay is displayed, alongside a bar graph of the $n$ worst performing trains. 

In this query, the company name, train ID, average company delay, average train delay, train on-time rate, and the gap of the train from the company's average delay. Unlike the first two reports, this report focuses on analyzing the performance of trains, which helps identify problematic trains.

The operation used in this query is once again, a \emph{dice} operation. In this report, the company dimension is fixed to the single company that the user wants to focus on, and the date dimension cuts all data not within the date range selected by the user. Resulting in a dice operation.

The corresponding SQL query used in this report is as follows. Note that this is the base SQL, including only the filter on company. The filter for date filtering is done separately in the application itself:

\begin{lstlisting}
CREATE INDEX ON fact_service (company_name);

WITH train AS (
    SELECT
        fsv.company_name,
        fst.train_id,
        COUNT(*) AS total_stops,
        SUM(fst.arrival_delay) AS total_delay,
        COUNT(*) FILTER (WHERE fst.arrival_delay = 0) AS on_time
    FROM fact_stop AS fst
    JOIN fact_service AS fsv ON fsv.rdt_id = fst.rdt_id
    WHERE fst.cancel_status IN ('none', 'departure-only')
    AND fst.arrival_delay IS NOT NULL
    AND fsv.company_name = 'Arriva' -- TO EDIT WITH SELECTED COMPANY
    GROUP BY fsv.company_name, fst.train_id
),
calc AS (
    SELECT
        company_name,
        train_id,
        ROUND(SUM(total_delay) OVER (PARTITION BY company_name)::numeric / SUM(total_stops) OVER (PARTITION BY company_name), 2) AS avg_company_delay,
        ROUND(100.0 * on_time / total_stops, 2) AS train_on_time_rate,
        ROUND(total_delay::numeric / total_stops, 2) AS avg_train_delay
    FROM train
)
SELECT
    company_name,
    train_id,
    avg_company_delay,
    train_on_time_rate,
    avg_train_delay,
    ROUND(avg_company_delay - avg_train_delay, 2) AS company_delay_gap
FROM calc
ORDER BY company_delay_gap ASC
LIMIT 5; -- EDIT HERE WITH NUM OF TRAINS TO SHOW
\end{lstlisting}

This report helps a company decide which trains are problematic and may need inspection.





\subsection{Report 4: Station Delay Recovery and Addition}
\label{subsubsec:station_delay_recovery}
The last report focuses on whether a station is able to recover from delays, or make delays worse. In the data warehouse, arrival delay and departure delay are both metrics included per-stop, alongside the station that these trains arrive and depart at. Arrival delay is not something a station can control, but departure delay is. If a train arrived severely delayed but departed with a low amount of delay, it is considered a good station at recovering from delay. Vice versa, a station that adds delay is considered a bottleneck. This report additionally separates the data by the time-of-day, as it is a strong factor in delay.

In the application, the user can pick a time-of-day, morning, afternoon, or night, the number $n$ of stations to show, then whether to show the $n$ delay recoverers or delay adders.

In this query, the station name, time of day, the average of the difference of the departure delay and arrival delay, and the total stops of the station are recorded. Unlike the other reports, this report focuses on analyzing the nature of the different stations, and identifying stations that are problematic in terms of causing delays, and stations which do well at recovering from the delays created by earlier stops.

The OLAP operation used in this query is a \emph{slice} operation on the time-of-day dimension, as it focuses the report on a single fixed time-of-day.

The corresponding SQL query used in this report is as follows:

\begin{lstlisting}
SELECT
    s.station_name,
    t.time_of_day,
    ROUND(AVG(fst.departure_delay - fst.arrival_delay), 2) AS avg_delay_change,
    COUNT(*) AS total_stops
FROM fact_stop AS fst
JOIN dim_station AS s ON s.station_code = fst.station_code
JOIN dim_time AS t ON t.time_key     = fst.arrival_time
WHERE fst.cancel_status = 'none'
  AND fst.arrival_delay IS NOT NULL
  AND fst.departure_delay IS NOT NULL
  AND t.time_of_day = 'morning'
GROUP BY s.station_name, t.time_of_day
ORDER BY avg_delay_change DESC;
\end{lstlisting}

This report shows which stations are bottlenecks and which help recover from delay, dependent on the time of day.
